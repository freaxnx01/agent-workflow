# New issues are born `needs-enrichment`, whoever files them — design

**Issue:** #549 · **Date:** 2026-10-19 · **Status:** approved (quick + headless enrich)

## Problem

The autopilot lane only picks up issues that carry `needs-enrichment`
(`scripts/lib/autopilot-candidates.sh:9-11,26`; `docs/AUTOPILOT.md:71-72`).
Issues filed by hand in the GitHub UI often don't get it, so the lane ignores
them without a trace. On freaxnx01/game-rhyflitzer (checked 2026-10-19): #357,
#308, #305 and #254 have no labels at all, #107 has only `area:modes`, while 45
siblings carry `needs-enrichment`.

## The other entry paths already label at birth

- **flowhub → bridge.** flowhub files an issue by calling bridge's
  `POST /api/capture/issue` (`flowhub: source/FlowHub.Skills/Bridge/BridgeSkillIntegration.cs:55,79-92`)
  and sends no labels. Bridge stamps the label:
  `bridge: internal/capture/capture.go:84-86`, "Every captured issue is born
  carrying needs-enrichment: the dispatcher's 'running /enrich is the approval'
  contract holds only if intake stamps it". The MCP `create_issue` tool does
  the same with no opt-out (`bridge: internal/mcp/tools_write.go:37-40`). The
  label goes in the **create** request itself
  (`bridge: internal/forge/github.go:282-289`), so the `issues.opened` event
  already carries it.
- **`/new`** creates the issue with `--label needs-enrichment`
  (`commands/new.md:42`).

So the only path without the label is the GitHub UI (or a bare
`gh issue create`). The fix must make that path behave like bridge: the label
is applied at intake, once, and removing it is a deliberate act.

## Options

1. **An `issues: opened` intake workflow** in the consumer applies
   `needs-enrichment` unless the issue already carries it, a pipeline label, or
   a plan. **Chosen.**
2. **The driver treats an unlabelled, never-enriched issue as a candidate.**
   Rejected. It widens what a paid nested session may be spent on from
   "explicitly marked" to "anything not marked otherwise", which is fail-open.
   It also diverges from bridge's contract (the label *is* the intake stamp),
   it is invisible on the issue, and it only helps the autopilot driver, not
   `/issues`, `/triage` or `/ai-funnel`, which also read the label.

## Design

### 1. `scripts/issue-intake.sh`

Env: `REPO`, `ISSUE_NUMBER`, `GH_TOKEN`; optional `DRY_RUN=1`.

1. Re-read the issue: `gh issue view <n> --json number,labels,body,author`.
   The re-read rather than the event payload gives a fresher state: a label
   someone added in the seconds before the job started counts.
2. Decide, in this order, with a pure function `intake_decision` (JSON on
   stdin, prints `label` or `skip <reason>`):

   | Rule | Result |
   |---|---|
   | `author.is_bot` is true | `skip opened by a bot` |
   | already carries `needs-enrichment` | `skip already labelled` |
   | carries any of `ai-implement`, `enrichment-ongoing`, `needs-human`, `parked`, `🧊 parked`, `roadmap`, `pipeline-paused`, or any `ai:`-prefixed label | `skip pipeline label <name>` |
   | body has a `## Implementation Plan` heading line | `skip already has an implementation plan` |
   | otherwise | `label` |

   Other labels (`bug`, `enhancement`, `area:*`, …) do **not** block intake. A
   human categorising a new issue is not a human deciding it needs no spec.
3. On `label`: `gh label create needs-enrichment --color d4c5f9 --description …`
   (`|| true`: it may exist; the colour matches `/new`'s Forgejo path,
   `commands/new.md:156`), then `gh issue edit <n> --add-label needs-enrichment`.
4. Print one line, `intake: #<n> labelled needs-enrichment` or
   `intake: #<n> skipped (<reason>)`, and write `decision=` / `reason=` to
   `$GITHUB_OUTPUT` when set.

Exit codes: `0` labelled or skipped by rule; `1` issue unreadable or label
write failed (the job goes red, so a missed intake is visible); `2` env
missing or invalid.

### 2. Reusable workflow `.github/workflows/issue-intake.yml`

`workflow_call` with `issue-number` (required), `pipeline-repo`,
`pipeline-ref`, `local-scripts`, `timeout-minutes` (default 5), the same
checkout pattern as `pipeline-health.yml`. Workflow-level
`permissions: contents: read`, job-level `issues: write`. Actions pinned by
full SHA. It uses `github.token`. Issues labelled with that token do not fire
other workflows, so the intake label cannot trigger `agent.yml`, which ignores
anything but `ai-implement` anyway.

### 3. Consumer stub, generated by `onboard-consumer.sh`

A new `build_intake_yml` writes `.github/workflows/issue-intake.yml`:

```yaml
name: Issue intake
on:
  issues:
    types: [opened]
permissions:
  contents: read
  issues: write
jobs:
  intake:
    uses: <pipeline-repo>/.github/workflows/issue-intake.yml@<ref>
    with:
      issue-number: ${{ github.event.issue.number }}
      pipeline-ref: <ref>
```

It is emitted on every onboarding, like the health stub. `/new` and bridge
already label every issue in every repo, so labelling hand-filed issues too is
the same convention, not a new one. A separate file rather than an `opened`
type on `agent.yml`, so the implement stub's trigger and permissions stay as
they are.

### 4. Docs

- `docs/AUTOPILOT.md`, "And per issue": the intake stub labels hand-filed
  issues; bridge/flowhub and `/new` already do.
- `docs/CONSUMER-SETUP.md`: a new section with the stub and what it skips.

## Out of scope

- Retro-labelling existing issues (operator one-off; issue body says so).
- Rolling the stub out to existing consumers. Re-running
  `onboard-consumer.sh` on a repo (e.g. game-rhyflitzer, #551) writes it;
  that is an operator action.
- Dogfooding the stub in agent-workflow itself. Its reusable workflow would
  share the file name, and its issues come from `/new`, which labels them.

## Testing

Layer-1, new `tests/run-issue-intake-tests.sh` (auto-discovered by
`tests/run-all.sh`), gh mocked, fixtures under `tests/fixtures/intake/`:
every row of the decision table, the write path (label create before edit),
dry run (no writes), unreadable issue (exit 1), failed edit (exit 1), missing
env (exit 2), `$GITHUB_OUTPUT`, and static checks on the reusable workflow
(trigger, least privilege, SHA pins, timeout). `tests/run-onboard-stub-tests.sh`
gains intake-stub assertions. `actionlint` and `shellcheck` stay clean.
